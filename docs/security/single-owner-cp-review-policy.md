# Single-owner C-P multi-agent review policy

**Category:** `C-P-MA-OWNER-ASSUMED-RISK`
**Scope:** the exact eight-phase, 135-command PR #118 passive Honda observation profile only
**Status of this branch:** proposed; ineffective until adopted on protected `main`

## Decision model

This policy addresses a single-owner project in which the sole operator is also the person who accepts residual risk. It creates an explicit owner-assumed-risk path for a narrow, fixed passive diagnostic. It does not call an AI report an independent human review, a vehicle-safety certification, or proof that a procedure is safe.

Three records remain separate:

1. **Independent human safety review** is an assessment by a qualified external human. It remains a distinct review category for experiments and deployment outside this exception. This C-P owner-directed category does not require one.
2. **Required technical reviews** are separate Codex and Claude reports, each bound to the exact reviewed commit, profile SHA-256, source map, command-manifest SHA-256 and eight phase IDs. ECC review is recommended but optional for this bounded C-P category only when it is unavailable. If unavailable, record `UNAVAILABLE`, a truthful reason, and the explicit attestation `no_completed_review_withheld: true`; do not create a review artifact. The owner attests that no ECC report completed or received for the exact scope is withheld; any such report must be included and validated even if unfavorable. Any supplied non-GO recommendation or unresolved critical/high finding blocks eligibility. This is an owner attestation, not an independently enforceable control: the validator checks the required field but cannot inspect external services or independently prove availability or truthfulness. The owner accepts that residual under this owner-assumed-risk category. These AI reports are not human safety certification.
3. **Owner risk acceptance** is Ben Reyes’s separate informed decision for one exact run, serial, electrical power state and reviewed source/profile hashes. The owner acknowledges the AI-review limitation and residual diagnostic risks. Owner acceptance is not a technical review and cannot waive the fixed safety boundaries.

The validator requires Codex and Claude reports, explicit truthful ECC status and non-withholding attestation when unavailable, exact hashes, private artifact permissions and matching C-P scope. Any submitted ECC report is fully validated. The validator cannot authenticate provider identity, inspect external services for withheld reports, independently prove ECC availability, or certify safety. Missing required reviews fail closed; optional ECC unavailability does not block C-P.

## Adoption and execution gates

This amendment is prospective and effective only after protected-main adoption. Before a live run, the controller requires clean `main` exactly matching fresh `origin/main`, Codex and Claude reviews bound to that exact commit, and explicit ECC status plus a validated report if one exists. It rechecks profile/source/manifest hashes and requests a fresh nonce-bound owner confirmation for each invocation. Each approval record has a unique ID. During the final challenge, SIGINT, SIGTERM and SIGHUP are held only until the bounded prompt resolves and an exact YES is atomically recorded in the owner-only host ledger. Pending signals are delivered immediately after the marker is durable, before post-prompt revalidation, capture creation or ADB; the same ID is rejected on later invocations. A non-YES response or prompt timeout does not consume the ID. SIGINT, SIGTERM and SIGHUP received during the prompt are deferred until the prompt resolves; after exact YES, the marker is persisted before pending signals are delivered. If ledger persistence fails, the runner stops before ADB. If no marker was created, the ID remains unused; a partial marker, if present, causes future validation to fail closed. Do not retry after this failure without resolving it and obtaining a new explicit owner decision. The validator cannot enforce a new record when no marker exists; this is an operator requirement. Interruption during the owner challenge stops before capture creation; no capture directory or failure card is created. SIGTERM/SIGHUP during collection or normal completion use the failure-finalization path; signals during the earlier policy-refresh stage retain default behavior before ADB or capture setup.

The host ledger is anchored to the current UID’s passwd home rather than the mutable `HOME` environment variable. It prevents ordinary accidental replay but is not tamper-proof against the local owner, who can modify or delete files in the owner account. The eligible profile is read-only unprivileged ADB. It contains eight phases and 135 fixed command entries; each command has a timeout no greater than 20 seconds and output limit no greater than 4 MiB. The current aggregate per-command ceilings are 2,425 seconds and 158,400,512 bytes. The controller also enforces a 3,600-second elapsed campaign deadline and a 300-second owner-prompt idle timeout. These are host-side software bounds, not measured resource use or proof of safe duration. `dumpsys` may consume head-unit resources; its bounded raw stdout and stderr are retained privately and may include window/app titles and identifying metadata. Logcat is summarized in memory, and source lines/stderr are not persisted. Diagnostic metadata may expose personal identifiers; normal CarPlay and factory Navigation transitions temporarily change infotainment state. Read-only intent does not guarantee zero side effects. The runner closes ADB stdin and handles command timeouts, output limits, and KeyboardInterrupt. After effective-policy validation completes, SIGINT/SIGTERM/SIGHUP during the final owner prompt are deferred for at most the five-minute prompt idle timeout; a non-YES response stops without consuming the ID, while exact YES consumes it before pending signals are delivered. If persistence fails before a marker is created, the same ID is technically still unused; the no-retry/new-owner-decision requirement is procedural. No capture directory or failure card is created during the prompt; if exact YES was not accepted, no approval ID is consumed, capture directory or failure card is created because collection has not started. After exact YES, the ID is consumed before capture creation. SIGTERM/SIGHUP during collection or normal completion triggers the stop/failure path. Once failure finalization has begun, later SIGTERM/SIGHUP are ignored while evidence is written. Signals during the earlier policy-refresh stage retain default behavior; at that point no ADB client or capture directory exists. SIGKILL, power loss, or process/runtime failure can still leave an incomplete checkpoint, and host cleanup cannot guarantee a remote child exits when the ADB client closes. Preserve incomplete private evidence and do not retry after interruption or transport loss.

The fixed power state is **ON mode, brake pedal not pressed, READY indicator absent**. The 2018 Honda Clarity PHEV owner's manual describes automatic engine start/stop during vehicle operation and defines READY as indicating the vehicle is ready to drive. Excluding READY is a conservative procedure choice; selecting EV operation does not prove that the engine cannot start. Head-unit and existing ADB availability in ON is unverified. The toolbox `id` applet and exact target `dumpsys`/`logcat` output behavior also remain unverified; in particular, Android 4.2.2 support for the fixed `logcat -d -t 500` form has not been demonstrated on this head unit. Any unavailable or unexpected operation must stop without substitution. A long ON-mode session may drain the 12 V battery; battery condition and ADB/head-unit tolerance have not been measured. A host-side 60-minute elapsed-session ceiling and five-minute owner-prompt idle timeout are software bounds, not evidence that a session of that duration is safe or that the battery will remain healthy. If the collector cannot proceed in ON, the required response is stop; READY, `adb root`, `su`, another privilege mechanism, or a configuration change is not a fallback. The owner controls all physical transitions. The session must be outdoors, stationary in Park, parking brake set, owner present, iPhone disconnected for baseline, and normal factory cluster/display/Navigation/audio confirmed. Before and after every collection phase, the live controller asks the owner to reconfirm Park, READY absent, no warning or abnormal cluster behavior, and normal visible display/cluster; baseline also asks that the parking brake is set and brake pedal is not pressed. If READY appears, the engine starts, any warning or abnormal behavior occurs, transport or process identity changes unexpectedly, or factory restoration is uncertain, stop and preserve evidence without retry. Loss of ADB between phases requires stop and ordinary-control restoration only; no retry or alternate transport. The campaign waits for each ADB client command to return before owner input; it does not stop or inspect a shared host ADB server, and cannot establish that server-side or remote child work has ceased.

The approved command manifest and source/profile pins may not be broadened by this policy. Exact serial, existing authorized ADB transport, unprivileged shell, private host-only raw evidence and existing stop/recovery rules remain mandatory. No capture runs while the owner performs a user-interface transition or waits for the next phase.

## Exclusions

This category does not authorize `adb root`, `su -c`, SuperSU execution, root reads, process attachment or instrumentation, Frida/ptrace, signals, memory writes, APK/helper installation, receiver changes, display control, HondaHack, firmware changes, CAN or other vehicle-control commands, warning interference, driving tests, deployment, or an automatic fallback. Privileged reads, HondaHack display observations, active Type111 instrumentation, receiver/display modification and deployment require separately scoped review and owner authorization under their own gates. `safeForHonda() == false` and `VEHICLE_DEPLOYMENT_NOT_AUTHORIZED` remain unchanged.

## Review record checklist

Each external review artifact stays outside public Git in owner-only private storage. The validator checks the report’s role label and SHA-256, reviewed commit, profile hash, source map, command-manifest digest, phase list, recommendation and required report fields. It cannot verify code-host identity or authenticity of an AI provider report. Review reports must cover:

- All command entries and legacy Android 4.2.2 ADB compatibility.
- Shell identity, process identity checks, command timeouts and output/resource ceilings, including the fact that legacy API-17 ADB exit codes do not reliably prove remote success.
- `dumpsys`, repeated diagnostics, logcat privacy and evidence handling.
- Process crash, ADB disconnection, stop/interruption behavior and restoration.
- Factory CarPlay and Navigation transitions, center display, cluster and warning behavior.
- PHEV electrical power state, ON/READY assumptions and unresolved head-unit stability risks.
- Tests actually run and assumptions that remain unverified.

No fabricated report, agent identity, tool version, finding disposition, human qualification or approval is accepted. The public status ledger records review availability and adoption state without publishing private reports or raw Honda evidence.
