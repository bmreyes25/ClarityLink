# Native CarPlay instrument-cluster integration: internet and firmware findings

**Status:** research and static comparison only. The Honda has not been contacted or modified. This document concerns standard CarPlay cluster guidance and an independent cluster map; CarPlay Ultra is a separate, later project. No CAN, B-CAN, F-CAN, ADAS, speedometer, warnings, or other vehicle-control systems are part of this plan.

## Target behavior: Volvo-style dual-screen Maps

[Volvo's June 2023 release](https://www.volvocars.com/us/media/press-releases/81CBD2EE643B547D/) confirms that an infotainment software update brought Apple Maps and supported navigation apps to the driver display in Volvo vehicles with Google built-in. The [2024 S60 hands-on](https://www.macrumors.com/2023/09/01/volvo-dual-screen-apple-maps-carplay/) illustrates the exact desired decoupling: an Apple Maps route remains visible behind the wheel while the center CarPlay screen shows Music, Podcasts, or another app. The review says that Volvo's cluster map includes route and trip-summary information, but **does not** itself show a written next-turn/exit instruction, distance to that maneuver, or lane guidance. Those text/maneuver fields are a separate milestone for the Clarity. The Volvo implementation is standard multi-display CarPlay, not evidence that the 2018 Honda receiver already implements it.

## What Apple actually supports

There are two native routes, with different requirements:

| Feature | iPhone output | Vehicle output | Introduced / source |
|---|---|---|---|
| Native turn-by-turn data | iAP2 Route Guidance metadata | Car draws its own maneuver, street, distance, status | Apple described next-turn metadata in iOS 10: [WWDC16](https://developer.apple.com/videos/play/wwdc2016/723/). Apple still describes this distinction in [WWDC19](https://developer.apple.com/videos/play/wwdc2019/252/). |
| Native cluster map or Apple Maps turn card | Additional CarPlay H.264 video stream(s), separate from the center stream | Vehicle decodes and composites each stream in an instrument-cluster-safe area | iOS 13 and **CarPlay Communication plug-in R15** APIs: [WWDC19](https://developer.apple.com/videos/play/wwdc2019/252/). |
| Third-party app cluster map/metadata | Navigation app adopts Apple's cluster scene and maneuver metadata APIs | Supported receiver presents the app's cluster content | [WWDC22](https://developer.apple.com/videos/play/wwdc2022/10016/), [WWDC25](https://developer.apple.com/videos/play/wwdc2025/216/). [Waze's help](https://support.google.com/waze/answer/9123774?hl=en) says Waze navigation is available in supported vehicles' instrument clusters. |

**2026-09-24 source check:** [Apple's WWDC25 session](https://developer.apple.com/videos/play/wwdc2025/216/) says navigation apps can provide maneuver metadata for a supported car to draw and can use a separate map area when they implement the relevant cluster scene. [Waze's own CarPlay help](https://support.google.com/waze/answer/9123774?hl=en) says Waze navigation is available on supported vehicles' instrument clusters. That supports keeping Waze in the later acceptance matrix, but does not prove that the current Waze/iOS combination will provide every map, maneuver, and distance field to this Honda. Test Apple Maps and Waze separately after receiver support exists.

Several often-quoted hardware requirements blend standard cluster integration with CarPlay Ultra:

| Claim | What applies to this Clarity project |
|---|---|
| Dual-video ECU / two H.264 decoders | A **separate CarPlay map stream** does require the receiver to negotiate, receive, decode, and place another H.264 stream. It does not necessarily require a separate automotive ECU or a second physical decoder block. A **metadata-only** native guidance display does not need a second video stream. The Tegra decoder is listed in this backup, but its concurrent capacity is unverified. [Apple's multi-stream explanation](https://developer.apple.com/videos/play/wwdc2019/252/). |
| 5 GHz Wi-Fi | Apple calls 5 GHz preferable for **wireless** CarPlay reliability; this car's existing wired CarPlay does not require it. [WWDC23](https://developer.apple.com/videos/play/wwdc2023/10150/). |
| GPU and bidirectional CAN integration | The receiver needs enough video and display capacity for a second map stream. Receiving iAP2 guidance or map video does **not** inherently require CAN access. This project excludes CAN and safety-critical systems. The vehicle-data integration described for CarPlay Ultra is a different scope. [WWDC19](https://developer.apple.com/videos/play/wwdc2019/252/), [WWDC23](https://developer.apple.com/videos/play/wwdc2023/10150/). |
| MFi authentication | Standard CarPlay already works here, so an authenticated path exists. That does **not** prove this receiver supports the newer multi-display communication APIs, and it does not establish whether a software-only upgrade is feasible. Apple reserves the full technical specifications for the [MFi program](https://mfi.apple.com/en/). |

## Comparison with the backed-up Honda receiver

| Requirement | Honda evidence | Verdict |
|---|---|---|
| Android output to instrument cluster | Captured second `HDMI Screen`, 800×480, and live Honda Hack casting | **Present**. We have a display destination. |
| Factory UI for semantic guidance | `HondaNavigationLib` `ITBTInformation`, `NavGuide`, `GuideDispDemand`; `ExternalDisplayOutService` callbacks | **Present**, but public setters can write B-CAN. A separate display-only adapter is needed. |
| CarPlay route metadata advertised and parsed | No Route Guidance feature handler found in deoptimized CarPlay service or `jmcs` strings/symbols. `turn_by_turn` in `jmcs` appears to be resource ownership, not a maneuver payload. | **Unproven/likely absent**. Requires a read-only iAP2 capability/session trace. |
| Multiple CarPlay display advertisement | `jmcs` `mc_carplay_app_init` at VA `0xaff09` creates `gMainScreen` once (call `0xaffd2`) and registers it (call `0xb02aa`); `AirPlayReceiverSessionScreen_CopyDisplaysInfo` at VA `0x287ae1` calls `ScreenCopyMain` at `0x287b0c`. | **One configured CarPlay display in this build**. Generic screen-array code is not evidence of an enabled second stream. |
| Second-screen callback | `libcarplay_proxy.so` `mc_carplay_proxy_screen_register` VA `0x1b7d` uses one global callback structure and rejects another registration after the flag is set. | **A concrete second blocker:** the Honda callback boundary is a singleton and needs a per-screen contract before it can forward a second decoded stream. See [focused audit](native/receiver-multidisplay-audit.md). |
| Independent CarPlay cluster stream decoder and surface | `libcarplay_proxy.so` and `jmcs` have screen callbacks; no car-specific second-screen registration/surface was found. NVIDIA H.264 decoder is listed in `media_codecs.xml`, but simultaneous capacity is unknown. | **Missing/unproven**. Cannot assert the hardware will sustain main + map + turn card. |
| Voice audio | User already verified CarPlay directions with casting. | **Works in current configuration**; must remain on existing CarPlay audio path for any retrofit. |

The most important constraint is [Apple's WWDC19 statement](https://developer.apple.com/videos/play/wwdc2019/252/) that iOS 13 multi-display features required adopting **R15 communication plug-in APIs**. This Honda build may predate that integration; we have no reliable R15 version identifier from the archive. The CarPlay main screen and Android cluster display being present does not imply the receiver can negotiate an iPhone-rendered cluster stream. The copied `j_config.xml` caps the main 800×480 screen at 30 FPS; that is a configuration value, not proof that a second decoder can run. The [receiver and decoder audit](native/receiver-multidisplay-audit.md) records the exact constraints and a bounded pixel-rate estimate.

## Useful open-source implementation reference

The [LIVI CarPlay receiver](https://github.com/f-io/LIVI/tree/143492a8e63e44aa0b17f39c0bd0a4ff20957885) is a current, independently developed **GPL-3.0** reference, not an Apple specification and not tested on this Honda. A sparse read-only source checkout and selected files are saved under `research/internet/livi-source` and `research/internet/livi` to preserve the investigated revision. Its details are leads for an offline test harness, **not** literal values to patch into `jmcs` without verifying this firmware's protocol.

- [`getInfo.ts`](internet/livi-source/src/main/services/projection/driver/cp/stack/getInfo.ts) declares one main display and optionally a second display. Its local names use stream types **110** and **111**, separate UUIDs, dimensions, view areas, and safe areas.
- [`cpStack.ts`](internet/livi-source/src/main/services/projection/driver/cp/stack/cpStack.ts) accepts a separate screen setup for type 111, opens an independent receiver, emits separate cluster video frames, and sends `showUI` for the cluster UUID with `maps:/car/instrumentcluster/map` after the main stream is ready. It can request a cluster key frame and stop that UI independently.
- [`identification.rs`](internet/livi-source/native/livi-helperd/crates/iap2-csm/src/messages/identification.rs) defines an iAP2 Route Guidance display component with an ID and text/storage capacities. [`route_guidance.rs`](internet/livi-source/native/livi-helperd/crates/iap2-csm/src/messages/route_guidance.rs) models start/update/maneuver/stop messages (`0x5200`–`0x5203`) with road, distance, ETA, maneuver and junction fields. These IDs and layouts are **third-party implementation evidence** until compared with official MFi materials or an observed compliant session.
- LIVI states that a normal MFi authentication path is required; it does not bypass that requirement. Its macOS operation needs a separate LIVI Link device. Replacing the Honda receiver with this application would be an entirely different, high-risk integration and would disrupt the current center display/audio path, so it is **not** the proposed retrofit.

## Concrete implementation path

**Primary target, independent map video:** obtain a receiver that supports the R15-era multi-display negotiation. It must advertise a cluster display with its own UUID, size, and safe area, process an additional screen setup and encrypted H.264 stream, create a second decoder/surface, and direct the iPhone to show cluster map/card content. Composite only into the navigation region of Android display 1 while preserving factory warnings and center CarPlay. The current `jmcs` cannot do this by a `CarPlayDisplay=0x08` toggle: it currently registers one `gMainScreen` and builds display information from that screen. Modifying only the Android cluster UI or only the `getInfo` display list would not produce a usable second image; the setup, decoder, control, rendering, and cleanup paths all have to agree. Hardware decode capacity and actual cluster safe-area geometry remain unverified.

**Separate guidance-data milestone (maneuver/street/distance):** determine, read-only, whether the Honda accessory identifies a Route Guidance display component and whether Apple Maps sends route messages. If messages already arrive but are discarded, hook only the decoded receiver event and map it into a new display-only Android navigation view on display 1. If the component is not advertised, an iAP2 receiver upgrade must add its identification capability, accept and parse updates, and then render them. Do **not** use `ITBTInformation.setNavGuide` or `setGuideDispDemand`: the factory implementation can send B-CAN. Preserve the original audio path. This is a real CarPlay metadata integration even though the car draws the arrow itself, but it does not meet the Volvo-style map target by itself.

There are three plausible ways to obtain the newer receiver behavior, ranked by risk: (1) an official Honda/Mitsubishi firmware/receiver update built for this hardware, if one exists; (2) a compatible new receiver library from the same hardware family with matching Binder/video/audio interfaces, if legally available; (3) substantial local receiver development using an independent reference and the backed-up firmware for compatibility. No evidence currently establishes that (1) or (2) exists, and (3) is a significant software project. The official MFi plug-in/API details are not fully public; a community implementation is useful for research but cannot be assumed to interoperate with the 2018 stack unchanged.

## Audit of a proposed three-component patch

The proposed *receiver → Android bridge → cluster* shape is directionally right, but its named switches and limits are not established for this car:

| Proposal | Finding from the Clarity backup / Apple documentation |
|---|---|
| Patch a capabilities XML/plist with `InstrumentClusterDisplay=True` | **Unsupported specific mechanism.** The model configuration has `CarPlayDisplay=0x08` and 800×480 values, and `jmcs` has a `CarPlay/ScreenProperties` configuration path, but no such named flag was found. `jmcs` currently registers only `gMainScreen`. Multi-display support must be added to the actual receiver capability and screen-registration/negotiation path, not assumed to follow a single XML edit. |
| iOS automatically starts a second stream and Honda discards it | **Incorrect as a current-state assertion.** Apple sends extra streams when the vehicle advertises and configures supported displays. No second Honda screen registration or second-stream setup was found. There may be no extra stream to intercept. |
| Install an Android service that maps a `SurfaceTexture` to a meter memory address | **Implementation detail invented prematurely.** The evidenced Honda Hack path is Android view rendering on display 1/`HDMI Screen`; screen casting uses shared memory and an `ImageView`. `disp_com_meter` appears to manage display-link control. Neither a meter pixel memory address nor a required `SurfaceTexture` path was established. A decoder output Surface in a display-1 window is a more evidence-based rendering target, but its exact API must be prototyped offline. |
| Tegra/NXP, 1 GB RAM, one H.264 hardware decode session | The backup identifies NVIDIA/Tegra H.264 codec support. The September 18 read-only car capture reports `MemTotal: 984580 kB`, confirming approximately 1 GB installed RAM. It does **not** establish an NXP alternative or a one-instance decode limit. Decoder concurrency must be measured before choosing a stream count or resolution. |
| Force 10–15 FPS/low bitrate in handshake to avoid crashes | `jmcs` reads a `MAX_FPS` screen property for its current screen, but the effect of changing it, the existence of an independent cluster rate setting, and iPhone acceptance are unverified. Ten or fifteen FPS is a hypothesis for an offline performance test, not a proven safe value or a first patch. |

The correct offline proof is a receiver capability model with **two distinct logical CarPlay displays**, separate screen setup and frame channels, a second decode/render pipeline, and unchanged main-screen/audio behavior. The Honda-specific bridge then places only the cluster map within the navigation region of display 1 and clears it on disconnect or route end. No vehicle write is justified until every link is demonstrated with the backed-up firmware and an offline test harness.

- `/proc/meminfo` reports `984580 kB` total RAM. Android SurfaceFlinger reports the built-in and HDMI screens, each 800×480. The HDMI capture shows Honda's factory cluster Menu page while Apple Maps routes on the center display; it is **not** a second Apple Maps stream. The center Maps screenshot and HDMI screenshot are local-only because they may reveal location or vehicle details.
- A fresh USB CarPlay reconnection was captured in [`carplay-events-sanitized.txt`](captures/20260918T153910Z-native-cluster-readonly/carplay-events-sanitized.txt). - Android 4.2.2 has no `media.codec` dumpsys service on this build, and unprivileged `/proc/<jmcs>/maps` was denied. These commands supplied no decoder concurrency result. Neither ordinary log snapshot contains decoded CarPlay maneuver fields. The captured screens are local evidence and may include personal content.

## Read-only evidence needed before a patch can be designed

1. Extract or observe the **actual iAP2 identification reply** (capabilities/message list) for this head unit, without changing or relaying it. This separates “phone does not send data” from “Honda discards data.” Logs captured so far do not include it.
2. Observe a stationary Apple Maps route start/turn/end and compare receiver traffic/events with its one-screen baseline. Look for Route Guidance messages and any second stream setup request. Keep personal route data local.
3. Determine the factory decoder's simultaneous H.264 instance limit and the display-1 navigation safe area using read-only service/codec reports and already captured frames. `media_codecs.xml` establishes a decoder, not how many concurrent streams it can sustain.
4. If metadata exists, write an offline parser and simulated display-only adapter with loss-of-signal clearing, then prepare a separately reviewable, reversible on-car artifact. If metadata does not exist, decide whether a new receiver stack can be tested on the Mac with an authorized MFi path before proposing any firmware change.

**Conclusion:** The Volvo-style iPhone-rendered cluster map requires a receiver upgrade or replacement. Route-guidance metadata may be an earlier independent milestone but does not replace the requested map. The current Honda software has a physical second display but only one proven CarPlay display. There is no evidence for a safe one-switch enablement, and a working native integration cannot be claimed from offline inspection alone.
