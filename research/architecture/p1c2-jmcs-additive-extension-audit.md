# P1-C2 — jmcs additive extension seam audit

**Scope and decision:** offline inspection of the hash-matched preserved 2018 Clarity receiver at starting commit `3f124ad34cb7f660c01078de499acb94c099698d`. **`NO_SUPPORTED_INTERFACE_FOUND_IN_REVIEWED_ARTIFACTS`** for a separate ClarityLink process to join the authenticated stock session, add Type111, or receive authentic navigation payloads while stock Type110 continues. This is a bounded artifact finding, not a claim that Type111 or custom software is impossible. The individual candidates and unknowns are in [the matrix](p1c2-type111-extension-matrix.json).

## Negotiation and Type111

`AirPlayCopyServerInfo` (`jmcs 0x282cd4`) ultimately reaches `ScreenCopyMain` (`0x2a17fc`) to build the one main display descriptor represented in `/info`. The CFArray and plist serializer can represent more data, but no external capability provider or supported mutator is present in the reviewed call chain. `AirPlayReceiverSessionCreate` (`0x284e58`) creates receiver-owned state. `AirPlayReceiverSessionSetup` (`0x2854e0`) dispatches Type100/101 audio and Type110 screen; its unsupported Type111 branch reaches the common loop continuation at `0x2861f6–0x286220` without creating a screen or appending a response stream. Type110 runs `AirPlayReceiverSessionScreen_Setup` (`0x287d5c`), then `_AddResponseStream` (`0x284db8`) adds its `dataPort`; `_requestSendPlistResponse` (`0x289f60`) serializes the receiver-owned response. A mutable CF dictionary is not an external SETUP hook.

`ScreenStreamStart` (`0x28e298`) and `ScreenStreamProcessData` (`0x28e2c8`) reach stock callback and media handling. `AirPlayReceiverSessionScreen_ProcessFrames` (`0x287d8c`) decrypts and forwards the Type110 frames. The per-screen key/IV and CTR context stay in `jmcs` (see [screen crypto](../carplay/honda-screen-crypto.md)). Neither authenticated `AirPlayReceiverSessionRef`, stream security context, listener FD, SETUP request/response object, nor Type111 key contract is exposed as an external, scoped handle. `AirPlayReceiverSessionSetDelegate` (`0x285040`) copies a whole 44-byte session delegate; the server delegate similarly copies one record. Replacement of either would displace stock ownership. Session finalization calls an internal Honda handler, not a subscriber list. Teardown parses known stream types and has no external Type111 close notification.

## Screen registration and media boundary

[The devmgr trace](p1c2-devmgr-registration-trace.md) shows `devmgr_app_register` (`0x8307c`) inserts an in-process callback record, and `dev_attach` (`0x81ff4`) chooses **one** highest-ranked callback for a device. `mc_ScreenStreamStart` (`0xbd628`) calls `mc_dev_attach` with `"CarPlay Screen"`. Another screen registration could outrank or replace the stock sink; it is not an independent observer. The precise producer, comparator, callback table, attached decoder and final Display 0 sink remain unproved because the relevant registry state is runtime-created and no supported snapshot is available. This does not turn the generic registration API into a cross-process interface.

The proxy library exposes `ScreenStreamInitialize` (`0x1130`), `ScreenStreamFinalize` (`0x1198`), `_ScreenStreamSetProperty` (`0x11ec`), `ScreenStreamStart` (`0x1260`), `ScreenStreamStop` (`0x12c4`), and `ScreenStreamProcessData` (`0x1318`). Each forwards to one stored function pointer. `mc_carplay_proxy_screen_register` (`0x1b7c`) checks the occupied flag at `0x1ba2–0x1baa`, returns `0x16` for a second registration (`0x1bce`/`0x1c10`), and copies six words (24 bytes) at `0x1be0–0x1c04`. `jmcs` imports proxy screen/audio/auth registration through PLT relocations, including screen register/unregister at `0x346acc/0x346ad0`. Exported C symbols are process-local callable ABI, not IPC. The analogous auth and audio owners are stock singleton callbacks; no observer or credential delegation is shown.

## Loader, IPC and sidecar audit

`jmcs` has `DT_NEEDED libcarplay_proxy.so` and imports `dlopen`, `dlsym`, and `dlclose` (PLT slots `0x346c00`, `0x346c04`, `0x346c64`). The enumerated loader call families in [loader sites](../runtime/jmcs-dlopen-sites.md) are generic/SQLite related; no CarPlay-specific loader name, constructor contract, session attach callback, or safe unload is demonstrated. SQLite extension loading is not an authorized CarPlay plugin route. Preserved receiver launch material lacks a verified init stanza, so there is no demonstrated supported vendor-module launch path. No unrelated binary was mixed into this callgraph.

Reviewed Java Binder inventory includes `CarPlayApService`, whose navigation callback carries only `onAbortCarPlayNavigation(boolean)` and `onCarPlayCallEnable(boolean)` from the bounded producers. Effective caller permission remains unverified; the declared payload is not a maneuver feed. ExternalDisplay output service does not bind an arbitrary media sink. The disconnected [socket inventory](../carplay/jmcs-runtime-sockets.md) records `jmcs` ownership of a port 5000 listener and unnamed Unix sockets but no CarPlay stream subscriber or session ID. Generic `socketpair`/`recvmsg` imports do not establish FD passing; inspected `recvmsg` callsites (`0x2a0836`, `0x2a59ce`) are generic receive/DNS paths. No message queue or shared-memory producer/consumer route for authenticated content was found. JMediaCore Binder payloads remain incompletely traced and are recorded as a specific unknown, not a supported seam.

## Custom implementation versus integration

ClarityLink already has a Type111 SETUP model (`src/claritylink-negotiation/type111_setup_contract.py`), transport receiver (`src/claritylink-transport/receiver_core.py`), lifecycle model (`src/carplay-session-model/project_lifecycle.py`), native receiver API (`native/include/claritylink/receiver.hpp`), and Android surface sink (`native/platform/android/android_surface_sink.hpp`). Those can implement a secondary parser/listener/decoder/renderer and cleanup **after** an authorized session-associated producer-to-consumer boundary exists. The missing integration contract is authenticated `/info` and SETUP participation, Type111 stream/security delegation, reliable close notifications, and a permitted output path. A separate receiver cannot claim the existing stock session merely by binding an unrelated socket or calling an exported local symbol. [The required contract](p1c2-receiver-extension-contract.md) lists the proof gates.

Public descendant research in [R5D](../runtime/r5d-clarity-receiver-lineage-closure.md) and [R5B](../runtime/r5b-type111-static-triage.md) identifies Civic/Accord/Acura similarities as **SIMILAR BUT UNPROVEN** for this receiver. No provenance-verified descendant Type111-capable `jmcs` or compatible CarPlay library is in the reviewed artifact set. No newer function can be attributed to this Honda, and no binary transplant is proposed.
