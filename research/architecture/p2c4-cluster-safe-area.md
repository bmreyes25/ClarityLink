## Measured versus synthetic geometry

The saved Honda Display 1 logical canvas is 800×480 on HDMI/layer stack 1. Saved SurfaceFlinger source/destination rectangles cover the whole logical frame. A paired physical photo shows vehicle indicators absent from the screenshot. It does **not** establish the physical cluster panel resolution, crop, transform, Navigation region, warning areas, layer priority, or orientation mapping. The 584×191 HondaHack layout is a different coordinate space and is not an OEM safe area. [Physical boundary review](../runtime/43t1-r4c-physical-safe-area-and-warning-boundary.md), [safe-area inventory](../navigation-safe-area.md), [warning evidence](../runtime/43t1-r4d-warning-zorder-static-evidence.md).

The [schema](p2c4-safe-area.schema.json) contains one explicitly **synthetic** 800×480 example: allowed rectangle `(100,60,600,360)` and protected cutout `(300,60,200,80)`. These values are test data only. There is no Honda configuration in the repository. The host gate rejects any provenance other than `SYNTHETIC_TEST_ONLY` and any nonidentity or rotated physical transform. This keeps unmeasured scaling/orientation from silently becoming an approved mapping. A future real configuration requires measured physical bounds and a separate, reviewed compositor/window contract.

## Rendering contract

The existing `ClarityLinkRenderer` accepts an optional [SafeAreaGate](../../src/claritylink-renderer/safe_area.py) in the host model. Existing callers with no gate retain their prior behavior. In the P2-C4 [simulator](../../src/claritylink-sim/simulate_safe_area.py), the gate validates the 800×480 logical geometry and supplies RGBA with alpha zero everywhere outside the allowed rectangle or inside a protected rectangle. The mock backend receives only this clipped frame. The invariant checked pixel by pixel is: **every nontransparent output pixel is inside the configured safe rectangle and outside every protected rectangle**. This is an output-pixel invariant in the host mock; transparency alone does not prove a full-frame Android window cannot obscure Honda UI. A real backend must also constrain its window/Surface bounds and prove compositing behavior.

On a surface-loss event or warning preemption, the renderer clears its current mock frame and rejects further submissions. On recovery/clear, it accepts a new frame only while validated geometry is present. A malformed config or frame geometry clears the output and withdraws admission until a valid configuration is explicitly supplied. `close()` clears and detaches. The simulator exercises normal frame, warning withdrawal/recovery, surface withdrawal/recovery and close; its output reports `visible_pixels=200000`, exactly the synthetic allowed rectangle minus its protected cutout. No Honda warning source is connected or simulated as authentic.

## Evidence and blockers

The focused tests cover schema/provenance rejection, invalid bounds, scale and rotation rejection, every pixel of the clipped frame, randomized rectangle containment, warning preemption, surface loss, recovery, and invalid-geometry withdrawal. The real Honda safe area remains `UNKNOWN`, as do exact physical scaling, stock warning z-order, and ordinary or native window admission. The host-only renderer does not authorize Honda output. Before any actual display use, P2-C1 through P2-C3 admission blockers must be resolved, a calibrated OEM physical safe region and warning precedence must be established, and the backend must show bounded window geometry plus cleanup on crash/display removal.

**Manual ECC-guided review:** verified provenance separation, fail-closed validation, protected-region exclusion, no stale frame after warning/surface loss, no real safe-area coordinates, and no Honda-facing command or target. Pixel alpha clipping is explicitly limited to the mock; it is not promoted to a physical-cluster safety proof. No independent ECC reviewer was invoked for this chunk.
