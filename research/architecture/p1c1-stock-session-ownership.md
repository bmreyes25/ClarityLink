# P1-C1 — stock CarPlay session ownership and boundary map

**Scope:** offline static evidence only, at PR #19 starting HEAD `ae9289b9f0fa16b1a5e843e88488f2d88b4567b1`. The stock receiver continues to own Type110 and center CarPlay. This map asks whether a *separate* ClarityLink process can receive authentic secondary video or navigation metadata. An exported symbol, callback, or service name is not by itself a cross-process session interface. No Honda command, write, execution, or configuration change was made.

## Artifact and provenance boundary

The PR worktree contains the reports but not the ignored proprietary artifacts. The sibling primary checkout supplied preserved read-only files: `extracted/system/system/bin/jmcs` SHA-256 `cbc7ba881648fb8ffdfcc4c1100a028345c37134a2ae3b9dff7d76572851c232`; `extracted/system-vendor/system/lib/libcarplay_proxy.so` SHA-256 `dc8bc5c19cf32a8e7edcc14c1d80e78bb96ca6ccc434229349c74590136bef66`; and decompiled CarPlay/ExternalDisplay packages under `research/decompiled` with manifests under `research/resources`. The hashes were rechecked. `xcrun llvm-objdump -t/-T` independently resolved `AirPlayReceiverSessionSetup` `0x2854e0`, `AirPlayReceiverSessionCreate` `0x284e58`, `AirPlayReceiverSessionScreen_Setup` `0x287d5c`, `AirPlayReceiverSessionScreen_ProcessFrames` `0x287d8c`, `ios_iap2_set_authenticated` `0x16e7e4`, `devmgr_app_register` `0x8307c`, and proxy `mc_carplay_proxy_screen_register` `0x1b7c`. These symbol confirmations do not re-prove every previously reported disassembly edge.

The principal existing evidence is [Step 42A](../../step-reports/42a-type111-display-stream-correlation.md), [R6C startup](../runtime/r6c-carplay-startup-chain.md), [R6D boundary audit](../runtime/r6d-authenticated-session-boundary-audit.md), [R3C extension audit](../runtime/43t1-r3c-session-addressable-extension-audit.md), [proxy audit](../runtime/43t1-r3c-libcarplay-proxy-interface-audit.md), [screen crypto](../carplay/honda-screen-crypto.md), and the [primary screen trace](../carplay/primary-screen-end-to-end.md). The exact stock USB-to-AirPlay object association, live Type110 listener endpoint, registered `CarPlay Screen` winner, media decoder/Surface, effective Binder caller permissions, route-guidance payload, and any Type111 security/framing remain missing.

## Session ownership

```mermaid
flowchart LR
  USB[USB host / iAP2 in jmcs] --> AUTH[factory I²C MFi auth in jmcs]
  AUTH --> ATTACH[authenticated iAP2 device state / attach]
  ATTACH -. exact object association unresolved .-> SERVER[AirPlay server and session in jmcs]
  SERVER --> INFO[/info: one main display descriptor]
  SERVER --> SETUP[SETUP: Type110 handled, Type111 skipped]
  SETUP --> KEY[Type110 key and AES-CTR context in jmcs]
  SETUP --> TCP[Type110 ephemeral listener / accepted socket]
  TCP --> FRAME[ScreenStream frame processing and proxy callbacks]
  FRAME --> SINK[stock selected sink / Display 0; final sink unresolved]
  SERVER --> BINDER[CarPlayApService Binder: app/UI status]
  BINDER --> EXT[ExternalDisplay AP control Binder]
```

## Candidate seams and what custom code could supply

The machine-readable [seam inventory](p1c1-session-seams.json) has individual A–M records, access classification, evidence, and decisive experiment. **There is currently no `SUPPORTED_CANDIDATE` for a separate ClarityLink process.** The narrowest *declared* external surface is `CarPlayApService` Binder, but effective caller admission remains unverified. Its `registerCallbackForNavi` transaction 64 registers a remote callback; `ICarPlayApServiceCallbackForNavi` contains only `onAbortCarPlayNavigation(boolean)` and `onCarPlayCallEnable(boolean)`. Preserved `OwnershipControl.java:520–530` and `PhoneControl.java:719–732` show those two boolean producers. It could provide status/lifecycle hints if caller access is later proven; it is not a route-metadata feed. The manifest says exported and names no component-level bind permission, which does not prove effective access. [Binder static contract](../carplay/carplayservice-api-surface.md); preserved decompiled interface and service implementation are in the sibling checkout.

| Desired custom function | ClarityLink can implement independently | Stock information and boundary required | Stock Type110 impact |
|---|---|---|---|
| Secondary video receiver/decoder/cluster renderer | Listener, framing/parser candidate, decoder, stale-frame handling, separate rendering and cleanup can be built offline. | Authenticated `/info`/SETUP mutation, Type111 endpoint/stream ID, compatible security material and lifecycle, and an admitted Display 1 pixel path. None crosses a supported observed boundary. | The code can *intend* to leave Type110 alone, but integration cannot be claimed without a genuinely additive session seam. |
| Maneuver/route metadata renderer | Route model, expiry, card rendering and separate-process logic are implementable. | Authentic Apple Maps/Waze maneuver values and source/session identity. Reviewed Binder callbacks contain status booleans, not maneuvers. iAP2 route guidance is an unverified possibility on this Clarity build. | Passive status reads could leave Type110 untouched if caller access is proven; no authentic route output follows. |
| Own navigation companion | Own destination, location, route calculation, transport and content can be designed. | Does not require stock session credentials if independent; does require separate permissioned phone-to-head-unit and Display 1 integration. | Potentially independent, but its output is **own navigation**, not authentic stock CarPlay secondary video or another app's active route. |
| In-receiver extension | Session-scoped observer/serializer and child listener are technically imaginable. | A *supported additive* extension ABI with same-identity create/Setup/close callbacks and authorized security delegation. None has been found. | Existing delegate/proxy replacement or binary/startup interposition would threaten Type110 and is outside this milestone. |

`devmgr_app_register` (`0x8307c`) is generic ranked registration. The winning entry for `"CarPlay Screen"` is not identified, and a new registration would compete rather than transparently subscribe. `ScreenStream` registration similarly holds one stock callback record and rejects a second registration. Neither can be called from a separately running process merely because a symbol is exported. See [registration](../carplay/device-registration.md), [proxy audit](../runtime/43t1-r3c-libcarplay-proxy-interface-audit.md), and [R3C](../runtime/43t1-r3c-extension-path-matrix.md).

## Decision and next experiment

**Decision: `P1_C1_EVIDENCE_MAP_COMPLETE`.** Best *declared but unverified for a new caller* seam A is the exported `CarPlayApService` Binder, specifically its navigation callback registration. It is not an authentic video or route metadata seam. The bounded producer-to-callback audit found only the two boolean producers above. The next decisive **offline** experiment is effective permission/signature and existing-client analysis; even a successful caller test later would yield only status booleans. Authentic content would require a new, proven source-to-external-consumer edge in a lawful, provenance-verified receiver artifact or documented extension API. No Honda contact or P1-C2 work follows automatically.
