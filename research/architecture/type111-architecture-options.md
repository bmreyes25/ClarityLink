## Decision

The best target architecture is **JMCS integration for the CarPlay control/session boundary, with a separate ExternalDisplay-host renderer adapter**. The protocol owner that knows the authenticated receiver session also owns Setup parsing and the Type110 KDF; placing Type111 beside those inputs minimizes new security/session transfer assumptions. The renderer remains a separate Android UI owner because ExternalDisplayOutService owns the existing Display 1 view tree. This is a split *runtime responsibility*, not the proposed network proxy: no network proxy route is established.

The only active, ready workstream today remains **digital-twin/offline models**. The selected target architecture is not deployable: jmcs entry is unresolved; Type111 Honda schema and key compatibility are unknown; and ExternalDisplay has no supported renderer handoff. `LD_PRELOAD` remains a parked fallback, not the chosen architecture.

## What would change the decision

- A proven supported Binder/Surface handoff from the current Honda APIs could remove the need for a host-side injection mechanism.
- A proven authenticated, transparent network interception path that can preserve Type110 and access compatible security state could make an external proxy competitive.
- A Honda Type111 request/response and crypto trace could invalidate assumptions borrowed from MHI2.
- A complete independent receiver with proven iAP2/MFi identity and simultaneous stock-center operation could support receiver replacement, but no current artifact establishes this.
