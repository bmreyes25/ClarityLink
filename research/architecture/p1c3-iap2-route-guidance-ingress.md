# P1-C3 — authentic iAP2 route-guidance ingress audit

**Decision: `P1_C3_STATUS_ONLY_NO_AUTHENTIC_GUIDANCE`.** In the reviewed, hash-matched 2018 Clarity artifacts, a CarPlay-related Android callback conveys two control/status booleans, while the route-shaped JSON and turn-by-turn interfaces use Honda-native navigation or Android Auto contracts. The sender of the Honda route response is not independently authenticated in the preserved code. No end-to-end iPhone maneuver producer → authenticated stock ingress → admitted external ClarityLink subscriber was established. This is a bounded finding; a missing iAP2 handler, protected specification, or session capture could change it. No Honda or iPhone operation occurred.

It says the newer display features require adoption of CarPlay Communication plug-in R15. The talk postdates the 2018 Clarity build and is platform context, **not** evidence that this firmware negotiated Route Guidance or that any app emitted it. Apple's [WWDC23 talk](https://developer.apple.com/videos/play/wwdc2023/10150/) likewise describes iAP2 metadata and separate navigation UI video. The public talks do not publish the Clarity's negotiated feature bits, message IDs, payload encoding, permissions, or app-specific emission behavior. Apple's [CPNavigationSession documentation](https://developer.apple.com/documentation/carplay/cpnavigationsession) describes navigation apps providing maneuvers, estimates and lifecycle to CarPlay; it is an iPhone app API, not a Honda-side subscriber ABI.

[Identification analysis](../iap2-identification.md) likewise leaves actual serialized IDs and negotiated values unknown.

Stock MFi authentication and CarPlay session ownership remain in `jmcs`; neither authenticated iAP2 channel nor AirPlay session handle crosses a demonstrated external boundary ([R6D](../runtime/r6d-authenticated-session-boundary-audit.md)). The examined `libcarplay_proxy.so` supplies singleton in-process screen/auth/audio callbacks, not navigation IPC. JMediaCore Binder symbols include generic `createChannel`, `sendData(Parcel*)`, `setListener` and `handle_data_received` (`jmcs 0x264c90`), but the route payload schema, channel ID, producer call chain, caller admission and lifecycle are untraced. It is **unknown**, not a supported route feed.

## Android navigation provenance and subscribers

The preserved CarPlayService manifest declares `CarPlayApService` exported without a component-level bind permission. Its `registerCallbackForNavi`/`unregisterCallbackForNavi` Binder transactions are 64/65; the implementation uses `RemoteCallbackList` (`CarPlayApService.java:109,1468–1490`), allowing callback bookkeeping and Binder-death cleanup. `OwnershipControl.java:520–530` and `PhoneControl.java:719–732` emit `onAbortCarPlayNavigation(boolean)` and `onCarPlayCallEnable(boolean)` respectively. The stock NavigationApService binds and registers (`NavigationApService.java:1289–1298`); `CancelRoute` consumes these booleans. Effective caller identity/signature admission, behavior for an additional no-APK native client, service binding environment and thread guarantees remain unverified. Even admission would deliver only status. No live Binder call was made.

`CarPlayApService.java:653–665` also requests `INavigationApService.requestGetRouteInfoCallback` and receives `onGetRouteInfo(String)` at `:2067–2073`. The **request/response intermediary** is `Navigation/RouteInfo.java`: it sends `com.honda.displayaudio.navi.action.GET_ROUTE_INFO` broadcast (`:101–116`) and receives `RES_ROUTE_INFO` (`:29–40, :119–154`) under the Honda factory navigation broadcast contract, contingent on `mNaviFlag`; the actual response sender package/UID is unverified. The CarPlay service parses the response only into `mNativeNaviRouteStatus` (`NavigationControl.java:81–101`). Its request queue serializes callbacks one at a time; adding a client is not passive observation. The word “CarPlay” in the requesting service does not establish iPhone origin for this Honda-native navigation contract.

`NavigationApService` names `com.honda.displayaudio.navi` at `:94`, exposes `ITBTInformation` and Honda meter structures (`HondaNavigationLib`), and has distinct Android Auto callback setup around `:1331–1345`. Honda TBT setters can affect meter/vehicle communication and are not a read-only route source. `HondaNavigationNaviLib`, `NavigationLib`, cluster/ExternalDisplay interfaces contain native map, route, status and display types, but no verified iPhone maneuver producer. `Navigation.apk`/`NavigationApService` are factory-navigation service artifacts, not proof of CarPlay metadata forwarding.

## Apple Maps, Waze and missing edges

Apple's WWDC19 talk explicitly illustrates Apple Maps instruction-card **video** on newly supported second streams, and distinguishes semantic iAP2 metadata. That is `SUPPORTED_BY_SOURCE` for Apple's platform capability, **not observed on this Honda**. Waze: `UNKNOWN` for this receiver and metadata route; no reviewed authoritative source or capture proves its emission here. No sanitized connected-session Route Guidance capture was found in the reviewed repository inputs. The current phone app's route generation, source identity and cancel/expiry state are consequently unavailable to a no-APK ClarityLink process.

The exact missing chain edges are (1) a negotiated, authenticated phone-to-`jmcs` Route Guidance message with decoded fields and provenance, and (2) a stock, permissioned subscriber API that a separate no-APK process can use without changing Type110. Even proof of edge (1) alone would mean an internal-only handler. A new ClarityLink adapter is therefore premature; [the adapter contract](p1c3-metadata-adapter-contract.md) states gates without inventing a production schema. The next decisive work is **offline** resolution of the hash-matched iAP2 control dispatch and JMediaCore channel consumers, plus a provenance-verified Route Guidance/Identification contract if lawfully available. Any future live observation needs separate authorization. P1-C4 has not been started.
