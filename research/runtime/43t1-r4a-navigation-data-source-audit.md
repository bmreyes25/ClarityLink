# 43T1-R4A — navigation data-source audit

Public-source snapshot reviewed **2026-10-03**. Prices and terms can change; check the linked provider pages before a paid or distributed implementation. `PUBLIC_API_DOCUMENTED` means the provider documents its **own** route data. It does not prove access to Apple Maps/Waze's active trip, a Honda app API, license permission for every cluster presentation, or real-time guidance correctness. This is an architecture comparison, not legal approval.

## Recommended data plan and phone boundary

R4B should use a **synthetic turn sequence with manual destination entry** to validate the renderer and stale-state behavior, with no provider key or live connection. For a later independent route source, a user-controlled companion could calculate its **own** route (MapKit only if cross-device terms allow, or OSRM/Valhalla/paid provider with reviewed terms) and send only next maneuver, distance, street, ETA, route generation and expiry. It must never claim parity with an independently active Apple Maps or Waze trip. If the user runs two navigation apps, routes may diverge; the UI must label its own provider and suppress stale guidance.

An iOS companion can request its own location with consent; [Apple documents background navigation location](https://developer.apple.com/documentation/corelocation/handling-location-updates-in-the-background) but an app must meet authorization/background-mode requirements. A future local Wi-Fi/Bluetooth/USB channel needs separate pairing, authentication, encryption, replay protection, revocation, and connectivity review. [iOS local network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) may require permission for local connections/Bonjour. None of those capabilities proves a Honda-side channel or authorizes a listener now. Minimize retained route/location data; avoid destination, coordinates, or API keys in logs and checked-in fixtures.
