## Linux and Android 4.2.2 findings

- The AOSP-era [toolbox build](https://android.googlesource.com/platform/system/core/+/018227f5394c3126f4a858596cb85dee1893b895/toolbox/Android.mk) includes `cat`, and its Android 4.2.2 [uptime implementation](https://android.googlesource.com/platform/system/core.git/+/android-4.2.2_r1/toolbox/uptime.c) reads `/proc/uptime`. An older Android common [kernel uptime implementation](https://android.googlesource.com/kernel/common/+/4764810c4544/fs/proc/uptime.c) uses `get_monotonic_boottime` and formats two decimal places. `/proc/uptime` measures elapsed time since kernel boot, including suspend; it does not use the Honda's wall clock. Honda vendor availability/format remains unverified.
- The kernel [boot ID](https://www.kernel.org/doc/html/v6.9/admin-guide/sysctl/kernel.html) is stable within one kernel boot and may be generated on its first read. Its presence depends on kernel configuration. There is no old boot ID in the private evidence, so a current boot ID cannot alone prove a later reboot. Two identical current reads can bracket one uptime observation and detect a reboot during the inspection, subject to UUID uniqueness. An unavailable or malformed source is inconclusive.
- `/proc/stat` `btime` is a [guest-wall-clock epoch time](https://man7.org/linux/man-pages/man5/proc_stat.5.html); it is not independent corroboration when the Honda clock may be wrong. The display turning off or vehicle POWER changing is not evidence of a kernel reboot.
- Linux [wait/reaping](https://man7.org/linux/man-pages/man2/wait.2.html) distinguishes a child exit from its parent's collection of status. A zombie has already terminated but retains a PID/status record until reaped. The prior failure did not save old PIDs, and PID values can be reused; `/proc/<pid>/stat` field 22 supplies start time only when an actual current PID has been safely identified. We do not guess PIDs or use process names or empty `ps` output as proof.
- AOSP defines [`AID_SHELL` as UID 2000](https://android.googlesource.com/platform/system/core/+/android-4.2.2_r1.2/include/private/android_filesystem_config.h), but vendor procfs mount and permissions can restrict visibility. Linux procfs [hidepid options](https://docs.kernel.org/6.2/filesystems/proc.html) illustrate why a negative process listing can be incomplete. A sufficiently narrow current-process mapping inspection without old PIDs may require broader enumeration and a separate reviewed authorization; it is excluded from Phase S.
- Linux [unlink semantics](https://man7.org/linux/man-pages/man2/unlink.2.html) allow an open file's data to remain until its last reference is closed after the pathname is removed. Therefore exact-path `rm` and ENOENT do not establish process termination. A completed process or a kernel reboot also does not by itself delete the executable pathname; Phase R actually observed it still present.

No process sweep, PID query, root, signal, diagnostic launch, write, deletion, fallback, or transport reconfiguration appears in the plan. Each command has a 12-second host timeout; all failures stop without another command or retry. The collector saves private mode-0600 exact stdout/stderr, status, decision, time, and redacted argv.

Let `F` be the original failure record's host finish time, `H` the independently attested historical error budget, `C` the current host-clock error budget, `T` the host UTC sample before the inspection, and `U` the observed uptime. The conservative latest possible old execution is `F + H`; the conservative earliest possible current boot is `T - C - (U + 0.01 seconds)`. Phase S reports `PREVIOUS_PROCESS_TERMINATION_ESTABLISHED` only if the latter exceeds the former by **more than one second**, the two boot IDs match, the current attestation is unexpired, and the host UTC clock agrees with monotonic elapsed time during the inspection. The proof assumes the independent bounds and chronology are genuine. An inconclusive inequality reports `PROCESS_POSSIBLY_ACTIVE`; missing sources report `BOOT_CONTINUITY_UNKNOWN`; conflicting IDs/clock step report `PROCESS_EVIDENCE_CONFLICT`; timeout and identity mismatch have distinct stop decisions.

Even a proven later kernel boot establishes termination of the **previous invocation only**. It does not prove no later relaunch or current executable mapping. Phase C remains `NO_GO` until that separate current safety question is resolved. The private clock-bound attestation must be created and independently reviewed before any Phase S authorization can be effective.
