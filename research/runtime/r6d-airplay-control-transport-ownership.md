# R6D AirPlay control transport ownership

`_AirPlayThread` creates the receiver server, installs its delegate and runs a CF loop. The AirTunes connection layer initializes an internal connection (`_connectionInitialize` calls `SocketSetKeepAlive`), dispatches messages via `_connectionHandleMessage`, and creates `AirPlayReceiverSession` internally (`0x28ae48`). The session-created delegate is copied into the server and invoked within the same process. The connection owns its socket/RTSP state; exact underlying fd opening is not fully traced here.

The `/info` route calls `_requestProcessInfo` (`0x28b68e`), `AirPlayCopyServerInfo`, then `_requestSendPlistResponse`; synchronous binary-plist/HTTP output reaches `SocketWriteData`/`writev` as proven in [Step 32](../../step-reports/32-airplay-info-phone-path.md). SETUP enters `AirPlayReceiverSessionSetup` and the same internal response serialization path per [R3A](43t1-r3a-setup-path-seam-map.md). Connection close calls `APSMFiSAP_Delete` for its pairing/SAP context (`0x289e04`); AirPlay session finalization tears down screen/control/timing resources per [Step 43I](../carplay/honda-session-delegate-lifecycle.md).

The R6B `CarPlaySessionTransport` can *conceptually* represent decrypted structured requests, responses, generation and close. There is no factory producer that transfers those operations, the connection, session identity or security context to another process. An internal fd alone would not transfer the paired protocol state or ownership. **Classification: `JMCS_OWNED_NONTRANSFERABLE` for the reviewed factory interface.** This is a supported-boundary decision, not proof that bytes can never be copied.
