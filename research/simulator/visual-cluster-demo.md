# Step 42F visual cluster demo

The demo is a static HTML page at `demo/type111/index.html`. Its data is generated by `src/claritylink-sim/export_visual_demo.py` from both modes of the Step 42E canonical replay and written to `demo/type111/replay-data.json`. It needs only Python's standard library and a local static HTTP server; the page makes no external requests.

Run from the repository root:

```sh
python3 src/claritylink-sim/export_visual_demo.py
python3 -m http.server 8000 --bind 127.0.0.1 --directory demo/type111
```

Open `http://localhost:8000`. The strict mode keeps the Type110/center placeholder active, reports Honda's stock unsupported Type111 branch, and shows no secondary frame. The hypothetical mode shows the replay's candidate listener/config/frame/render events and a schematic map-like SVG illustration in the mock Display 1 inset. That illustration is selected from structured replay output, but is not an actual decoder output. The renderer mock submission and the synthetic frame source are shown distinctly in the evidence ledger and disclaimer.

The page includes an evidence ledger, semantic timeline, and unknown register. It labels the Type110 baseline `HONDA_CONFIRMED`, the candidate response profile `MHI2_DERIVED_HYPOTHESIS`, generated state and visuals `SYNTHETIC_TEST_VALUE`, and unproven protocol or hardware behavior `UNKNOWN`. In hypothetical mode it lists candidate response field names while labeling their profile as MHI2-derived and the request values synthetic. It calls out response schema, display-stream correlation, Type111 security/KDF, ExternalDisplay handoff, crop/mask, and jmcs load seam. Live Type111, jmcs no-op, and actual ExternalDisplay render remain `NOT_READY`; LD_PRELOAD is `PARKED`.

The generated JSON includes only state and semantic event summaries from the replay. It excludes media bytes, key material, Honda captures, firmware, and personal/session values. `tests/integration/test_visual_cluster_demo.py` checks both replay modes, visible evidence categories and unknowns, and keeps all live-readiness gates closed. Browser preview checked both Strict Honda and Hypothetical Type111 modes at `http://127.0.0.1:8765/` during Step 42F.

Step 42G adds a host decoder status to the payload. The synthetic illustration remains a fallback, not a decoded video frame. The page displays `SYNTHETIC FRAME SOURCE — HOST DECODER UNAVAILABLE` when FFmpeg is absent; otherwise it says that no valid H.264 test media was generated by the replay. The current replay bytes are parser fixtures only. No decoder output is claimed.

Step 42H capability check confirms FFmpeg is absent on the current host; libx264, H.264 decoder, and RGBA output are therefore unavailable. The actual media test skips and the demo continues to show the fallback. No live or Honda decoding claim is made.

Step 42I reran the synthetic encode/decode path on a Mac with FFmpeg 9.0.2/libx264. The replay JSON now reports `HOST-DECODED SYNTHETIC H264` for the separate 320×180 synthetic test pattern and records successful mock Display 1 submission. The inline map remains an SVG schematic, not a rendering of those decoded pixels. The status does not indicate a Honda Type111 stream or advance any live gate.

Step 42J adds an actual synthetic ScreenStream fixture validation to the generated JSON. `--screenstream-h264` creates a valid test pattern in memory, builds synthetic avcC and AVCC packet bodies, wraps modeled opcode 1/0 messages, parses them, converts AVCC to Annex-B, decodes with FFmpeg 9.0.2, and submits the RGBA frame to the Display 1 mock. The demo displays `HOST-DECODED SYNTHETIC H264 VIA SCREENSTREAM FIXTURE` only on full success. This refers to synthetic modeled input and mock submission, not Honda output or real CarPlay frames; the SVG itself remains schematic. The static page explicitly says ExternalDisplay handoff is unproven and keeps all live gates NOT READY.

## Step 42K — actual decoded pixels in the visual twin

The exporter now takes the exact `DecodedFrame` retained by the mock Display 1 renderer and encodes those RGBA pixels into a standard-library PNG. It writes only to ignored `demo/type111/runtime/type111-frame.png`; `replay-data.json` carries dimensions, RGBA byte count, pixel SHA-256, source, and evidence label, never media bytes. The browser displays the PNG in Hypothetical Type111 mode only after the artifact loads and its dimensions match metadata. The aspect ratio is preserved with `object-fit: contain`. Strict Honda mode remains empty.

Run `python3 src/claritylink-sim/export_visual_demo.py --screenstream-h264` to regenerate the full fixture, decode, mock-render, PNG, and replay metadata. The exporter removes old runtime outputs before any attempt; unavailable decoder, decode failure, or artifact failure cannot leave a previous successful frame visible. Missing artifacts fall back to the labeled schematic. Tests unpack the PNG and compare recovered pixels and SHA-256 against the source RGBA, verify Type110/audio isolation, check strict mode, and exercise stale-artifact cleanup. The visible pixels remain `SYNTHETIC_TEST_VALUE`, not Honda/CarPlay/map content. Honda Type111 wire behavior, jmcs integration, and real ExternalDisplay rendering remain unknown and not ready.
