# Host H.264 decode stage (Step 42G)

The twin now has an optional host decode adapter in `src/claritylink-sim/host_h264_decoder.py`. It accepts a bounded Annex-B access unit plus explicit dimensions/timestamp and, when FFmpeg is installed, requests one RGBA frame on stdout. The output is validated against the existing `DecodedFrame` contract before it can reach the Display 1 renderer mock. It uses argument arrays (no shell), a timeout, bounded input/dimensions, and does not persist media.

`generate_synthetic_h264()` can create one synthetic `testsrc2` frame through FFmpeg/libx264 into memory. No generated media is committed. Generation and decode are optional because this host has neither FFmpeg nor a Python video decoder; the real encode/decode test is explicitly skipped with that reason.

The Step 42E replay's AVCC-like bytes are parser fixtures, not a valid H.264 access unit. They are deliberately not sent to a real decoder. Consequently the canonical visual twin still uses the synthetic pattern fallback, and reports `HOST_DECODER_UNAVAILABLE` here. If FFmpeg exists elsewhere, it reports that the backend is available while still stating that no valid H.264 test media was generated/decoded by this replay. A fake subprocess test verifies adapter-to-frame-to-renderer wiring, but is not counted as actual decoding.

The decoder requires SPS and PPS NALs in Annex-B, one access unit, dimensions supplied by the caller, and emits one frame. This is only an offline test boundary. It does not establish Honda VideoConfig geometry, Honda Type111 framing, crypto, timing, or decoder compatibility. Type110 and audio isolation remain covered by the replay tests. Live Type111, jmcs no-op load, and ExternalDisplay output remain NOT READY.

Step 42H added a read-only capability probe for FFmpeg version, libx264 encoder, H.264 decoder, and RGBA pixel format. On the current host, FFmpeg/ffprobe and all Python decoder packages are absent; all four capabilities report unavailable. No synthetic media was generated and actual encode/decode was skipped explicitly. The fake-process adapter check remains adapter verification only, not decode evidence. See `step-reports/42h-ffmpeg-synthetic-h264-validation.md`.

Step 42I ran the real path on macOS with `/opt/homebrew/bin/ffmpeg` 9.0.2 and libx264. A `testsrc2` 320×180 synthetic frame was encoded in memory as Annex-B H.264, decoded to an RGBA buffer of 230,400 bytes, and submitted to the mock Display 1 backend. The test passed. FFmpeg/libx264 output is synthetic test evidence only and is separate from the Step 42E parser fixture. No encoded/raw frame file was retained. The visual JSON records `HOST-DECODED SYNTHETIC H264`; the page still distinguishes its schematic illustration from decoded pixels and Honda output. See `step-reports/42i-real-synthetic-h264-decode.md`.

Step 42J adds a media-backed synthetic ScreenStream fixture. It derives avcC and a four-byte length-prefixed AVCC IDR access unit from generated SPS/PPS/VCL NALs, wraps them in modeled 128-byte opcode-1 and opcode-0 headers, and passes them through `HondaScreenReceiverCore`. The resulting Annex-B access unit is decoded by FFmpeg 9.0.2 and submitted as a 320×180/230,400-byte RGBA frame to mock Display 1. This is plaintext synthetic transport modeling (`PLAINTEXT_SYNTHETIC`), not Honda protocol evidence. No media files are retained; the demo metadata reports the ScreenStream path only after the whole pipeline passes. See `step-reports/42j-valid-h264-screenstream-fixture.md`.
